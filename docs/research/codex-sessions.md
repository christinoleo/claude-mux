# Where a Codex session keeps its conversation

Research note, 2026-10-16, for
[#142](https://github.com/christinoleo/claude-mux/issues/142) (map
[#140](https://github.com/christinoleo/claude-mux/issues/140)).

The question: where does a Codex session (OpenAI's `codex` CLI in a tmux pane)
keep its conversation, what does it hold, and how does that map onto what
`src/transcript/` and `src/usage/` read from a Claude Code JSONL?

Only primary sources were used: the `openai/codex` source at two pinned
commits, OpenAI's official Codex docs, and the `codex-cli 0.160.0` installed on
omarchy, which is **not logged in**. No Codex session has ever run on this
machine, so nothing here was observed live. Every claim cites the source file
it comes from. Anything that is inferred rather than read is marked
**unverified**.

## Summary

- **One JSONL file per thread (Codex's word for a session)**, at
  `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-<local time>-<thread id>.jsonl`,
  where `CODEX_HOME` defaults to `~/.codex`. The thread id is a UUIDv7. The
  file is created lazily, at the latest when the first prompt is recorded. A
  subagent is a thread of its own with a file of its own in the same tree.
- **Each line is `{timestamp, ordinal?, type, payload}`**, where `type` is one
  of `session_meta`, `response_item`, `event_msg`, `turn_context`,
  `compacted`, `token_usage_record` and a few others. The first line is
  `session_meta` (id, cwd, CLI version, source, git info, and Codex's whole
  system prompt, so it is several KB).
- **There are two dialects, and 0.160's TUI writes the newer one.** Since 0.147
  the TUI starts every non-ephemeral thread as `history_mode: "paginated"`.
  Such a file records each finished turn item as an `event_msg` of type
  `item_completed`, carrying a typed item: `UserMessage`, `AgentMessage`,
  `Reasoning`, `CommandExecution`, `FileChange` (with a unified diff per
  file), `McpToolCall`, `CollabAgentToolCall`, `ContextCompaction`, and more.
  Older files are `legacy` and record `user_message`, `agent_message`,
  `agent_reasoning`, `patch_apply_end` events instead. Both also carry the raw
  model items (`response_item`). A reader should key off `session_meta.payload.history_mode`.
- **Edits come with diffs.** A `FileChange` item maps absolute paths to
  `add {content}`, `delete {content}` or `update {unified_diff, move_path}`,
  where `unified_diff` is hunks without `---`/`+++` headers. That is enough
  for the Changes pane, the same way `structuredPatch` is for Claude.
- **Usage is per response and per turn.** `token_usage_record` lines (since
  0.153) give each response's `usage` plus running turn and thread totals;
  `token_count` events give the running total, the context window and the
  plan's rate-limit windows. The model is not on those lines: it is on the
  `turn_context` line written once per turn. OpenAI's `input_tokens`
  **includes** the cached tokens, unlike Anthropic's.
- **Past sessions can be listed without opening files.** Codex keeps a SQLite
  index, `~/.codex/state_5.sqlite`, whose `threads` table has the rollout
  path, cwd, title, first user message, preview, git branch, model, tokens
  used, source and timestamps. Names given with `/rename` or generated by the
  TUI are also appended to `~/.codex/session_index.jsonl` (last entry wins).
  Reading the head of each rollout file is Codex's own fallback.
- **Resume is `codex resume <thread id or name>`.** It prompts for a working
  directory when the current one differs from the session's, unless
  `tui.resume_cwd` is set. A thread being written by a live process holds a
  file lock at `~/.codex/thread-writer-locks/<thread id>.lock`, and a second
  writer is refused.
- **A running pane's thread can be found three ways:** from Codex's hooks
  (`session_id` is the root thread id, `transcript_path` the rollout path),
  from the process's open files (the writer lock and the rollout file), or
  from the state database by cwd and recency. Hooks are the one that works
  everywhere. Caveat: if a shared Codex daemon is running, the session runs
  inside the daemon, not the pane's process (§2.4).
- **Codex has subagents** (on by default). The parent's log records the
  `spawn_agent`/`wait`/`close_agent` calls as `CollabAgentToolCall` items with
  the child's thread id, nickname and role. The child's own rollout starts
  with a `session_meta` whose `source` is
  `{"subagent":{"thread_spawn":{"parent_thread_id":…}}}`. Codex's
  `SubagentStart`/`SubagentStop` hooks fire for them, with the child's
  transcript path.
- **Update notice.** The TUI checks GitHub (or Homebrew) at most every 20
  hours and caches the answer in `~/.codex/version.json`. When newer, it shows
  a blocking update picker *before* the session starts (when it knows how
  Codex was installed), and an "Update available! 0.160.0 -> X / Run `npm
  install -g @openai/codex` to update." card in the transcript. `codex update`
  runs the update from a shell.

## 1. Where the log is written

### 1.1 The path

`precompute_new_rollout_path()` builds
`codex_home/sessions/<year>/<MM>/<DD>/` from the **local** date, and the file
name from `RolloutFileName::render()`
([CX rollout/src/recorder.rs](https://github.com/openai/codex/blob/a956835d02/codex-rs/rollout/src/recorder.rs)
around line 1723,
[CX rollout/src/rollout_file_name.rs](https://github.com/openai/codex/blob/a956835d02/codex-rs/rollout/src/rollout_file_name.rs)):

```
~/.codex/sessions/2026/10/16/rollout-2026-10-16T15-00-00-019a2b3c-4d5e-7f60-8a1b-2c3d4e5f6071.jsonl
```

- The time in the name is local time with `-` for `:`; the timestamps inside
  the file are UTC (`2026-10-16T18:00:00.000Z`, `JsonlWriter::write_rollout_item`
  in `recorder.rs`).
- After the time comes the thread id. A thread reverted with `thread/revert`
  gets a new file named `<thread id>_<rollout id>`; ordinary files use one id
  for both (`rollout_file_name.rs`, `protocol/src/thread_id.rs`).
- `CODEX_HOME` overrides `~/.codex` (`utils/home-dir/src/lib.rs`).
- Archived threads move to `~/.codex/archived_sessions/`
  (`ARCHIVED_SESSIONS_SUBDIR`, `rollout/src/lib.rs`).
- Unlike Claude Code's `~/.claude/projects/<launch dir>/`, the directory says
  nothing about the project: the cwd is only inside the file (and in the
  state database). claude-mux cannot derive the path from cwd and id; it has to
  be told it, find it by id (glob `sessions/*/*/*/rollout-*-<id>.jsonl`), or
  look it up in the database.

### 1.2 When it appears

New threads defer creating the file until `persist()` is called
(`RolloutRecorder::new`, `recorder.rs` line 869: "defers file creation/open
until an explicit `persist()` call"). The session calls
`ensure_rollout_materialized` when it records a user's input
(`core/src/hook_runtime.rs` around line 764) and whenever a hook needs a
`transcript_path` (`Session::hook_transcript_path`,
`core/src/session/mod.rs` line 5078). So a Codex that was started but never
given a prompt may have no file yet, as with Claude Code.

### 1.3 Compressed and migrated files

Two storage changes exist in 0.160 and on `main`, both **off by default**
(`features/src/lib.rs`: `local_thread_store_compression` and
`background_paginated_rollout_migration`, `Stage::UnderDevelopment`,
`default_enabled: false`, unchanged on `main`):

- Compression rewrites rollouts not touched for 7 days as `.jsonl.zst`
  (zstd level 3; `rollout/src/compression.rs`, `MIN_ROLLOUT_AGE`). A reader
  that globs only `*.jsonl` would lose them if the feature is ever turned on.
- Migration rewrites legacy files into the paginated dialect.

### 1.4 The other files under `~/.codex`

| File | What it holds | Source |
|---|---|---|
| `state_5.sqlite` | `threads` table: one row per thread (§5.1). Also `thread_spawn_edges` (parent → child) | `state/src/sqlite.rs`, `state/migrations/0001…0058` |
| `thread_history_1.sqlite` | An index of paginated rollouts (byte offsets per ordinal) used for paging. The JSONL stays the source of truth | `thread-store/src/local/thread_history.rs` |
| `session_index.jsonl` | Append-only `{id, thread_name, updated_at}`; the last entry for an id wins | `rollout/src/session_index.rs` |
| `thread-writer-locks/<thread id>.lock` | Held with an OS file lock while a process writes that thread | `rollout/src/writer_lock.rs` |
| `version.json` | The update check's cache (§9) | `tui/src/updates_cache.rs` |

`sqlite_home` (config) or `CODEX_SQLITE_HOME` moves the databases; the default
is `CODEX_HOME` (`core/src/config/mod.rs` around line 4087). The installed
0.160.0 on omarchy has created `state_5.sqlite` with exactly the columns listed
in §5.1 (checked read-only with `sqlite3 -readonly ~/.codex/state_5.sqlite
".schema threads"`; zero rows).

## 2. Finding a running pane's thread

### 2.1 The id

Thread ids are UUIDv7 (`ThreadId::new`, `protocol/src/thread_id.rs`). The
session id in the meta and in hooks equals the **root** thread's id: a root
session uses `SessionId::from(thread_id)`, a subagent inherits its root's
(`core/src/session/session.rs` around line 909: "session_id is equal to the
root thread's ID").

### 2.2 From hooks (works everywhere)

Codex runs Claude-style command hooks. Every payload carries `session_id`,
`turn_id`, `transcript_path` (the rollout path, or null for a store with no
local file), `cwd`, `model` and `permission_mode`; tool and permission events
add `agent_id`/`agent_type` for a subagent's calls
(`hooks/src/schema.rs`, e.g. `PreToolUseCommandInput`, `PermissionRequestCommandInput`;
`core/src/hook_runtime.rs`). Asking for `transcript_path` materialises the
file (§1.2), so a `SessionStart` hook always sees a path that exists. This is
the analogue of the `transcript_path` claude-mux's hook already records for
Claude, and it is the reliable route. (Hook trust and setup belong to #141.)

### 2.3 From the process (Linux, no hooks)

**Unverified live**, read from source:

- The writer lock: a live writer opens and locks
  `~/.codex/thread-writer-locks/<thread id>.lock` when the thread is created
  or resumed and holds it for its life (`thread-store/src/local/live_writer.rs`,
  `WriterLockCoordinator::acquire` in `rollout/src/writer_lock.rs`, which uses
  `File::try_lock`). So `/proc/<pid>/fd` of the process running the session
  should show the lock file, naming the thread id even before the rollout
  exists, plus the rollout file once it is open (`RolloutWriterState` keeps
  its `JsonlWriter` open, `recorder.rs`). A process running subagents holds
  their locks too; the root is the one whose rollout has no `parent_thread_id`.
- Commands Codex runs get `CODEX_THREAD_ID=<thread id>` in their environment
  (`protocol/src/shell_environment.rs`).

### 2.4 The daemon caveat

The TUI does not always run the session itself. If a shared app-server daemon
is listening on its socket under `CODEX_HOME`, the TUI connects to it and the
thread, its rollout writer and its hooks live in the daemon process
(`app_server_target_for_launch`, `maybe_probe_default_daemon_socket` in
`tui/src/lib.rs`; `tui/src/startup_orchestration.rs`). In that case
`/proc/<pane pid>/fd` shows nothing, and a hook's environment is the daemon's,
not the pane's (so `TMUX_PANE` would be wrong; **unverified**). With no daemon
running, the TUI embeds the server in its own process. `codex --no-daemon`
forces the embedded server ("Run the interactive CLI without the shared
background server", CLI reference; `tui/src/daemon_startup.rs`), and so does
any `-c` override (`config_exclusion` in the same file). **claude-mux should
launch and resume Codex with `--no-daemon`.**

### 2.5 From the database

`threads` has `cwd`, `rollout_path`, `source` and `updated_at_ms`, so the most
recent `cli` thread in a pane's cwd is a guess. It is ambiguous when two Codex
panes share a folder; use it only as a last resort.

## 3. The line format

### 3.1 The envelope

```json
{"timestamp":"2026-10-16T18:00:05.014Z","ordinal":6,"type":"response_item","payload":{…}}
```

`RolloutLine` is `timestamp`, optional `ordinal`, then the item flattened as
`type` + `payload` (`history/src/lib.rs` `RolloutLine`;
`history/src/rollout_payload.rs` `RolloutItemWire`, `tag = "type"`,
`rename_all = "snake_case"`). Paginated files number every line from 0 in
`ordinal`; legacy files have none (`RolloutOrdinalState::for_new_rollout`,
`recorder.rs`).

| `type` | Payload | Persisted when |
|---|---|---|
| `session_meta` | `SessionMeta` + `git` (§3.2) | first line; later copies can come from fork history (`rollout/src/list.rs` comment, line ~1157) |
| `response_item` | A Responses API item: `message`, `reasoning`, `function_call`, `function_call_output`, `custom_tool_call`, `custom_tool_call_output`, `local_shell_call`, `web_search_call`, `image_generation_call`, `compaction`, … | always (`should_persist_response_item`, `rollout/src/policy.rs`) |
| `event_msg` | An `EventMsg`, filtered by dialect (§3.3) | see §3.3 |
| `turn_context` | Per-turn settings: `turn_id`, `cwd`, `model`, `effort`, `approval_policy`, `sandbox_policy`, … | once per real user turn (`core/src/session/mod.rs` line ~4745: "Persist one `TurnContextItem` per real user turn") and after compaction |
| `compacted` | `{message, replacement_history, window_number, …}` | each compaction |
| `token_usage_record` | Per-response usage (§6) | each response with usage, since 0.153 |
| `inter_agent_communication`, `world_state`, `retained_context`, `security_risk_score`, `realtime_item` | internal | not needed by claude-mux |

`parse_rollout_line()` (`rollout/src/lib.rs`) is the canonical decoder; Codex
skips lines it cannot parse. claude-mux should do the same, as its Claude
parser does.

### 3.2 `session_meta`

From `SessionMeta`/`SessionMetaLine` (`protocol/src/protocol.rs` lines
3123–3241) and the recorder (`recorder.rs` lines 935–967):
`session_id`, `id` (thread id), `forked_from_id`, `parent_thread_id`,
`timestamp`, `cwd`, `originator`, `cli_version`, `source`, `thread_source`,
`agent_nickname`, `agent_role`, `agent_path`, `model_provider`,
`base_instructions` (`{text}`: Codex's full system prompt, several KB),
`dynamic_tools`, `memory_mode`, `history_mode` (`"legacy"` when absent),
`multi_agent_version`, and `git` (`commit_hash`, `branch`, `repository_url`).

`source` is serialised lowercase: `"cli"` (the TUI), `"vscode"`, `"exec"`
(`codex exec`), `"mcp"`, or an object such as
`{"subagent":{"thread_spawn":{"parent_thread_id":…,"depth":1,"agent_nickname":…,"agent_role":…}}}`
(`SessionSource`, `SubAgentSource`, `protocol.rs` lines 2826–2923). Codex's own
"interactive" filter is `cli`, `vscode`, and the custom `atlas`/`chatgpt`
(`INTERACTIVE_SESSION_SOURCES`, `rollout/src/lib.rs`).

The model is **not** in `session_meta`; it first appears in `turn_context`.

### 3.3 The two dialects

`should_persist_event_msg()` decides which events reach the file
([CX rollout/src/policy.rs](https://github.com/openai/codex/blob/a956835d02/codex-rs/rollout/src/policy.rs)):

- **Both dialects:** `task_started` (Rust `TurnStarted`), `task_complete`
  (`TurnComplete`), `turn_aborted`, `token_count`, `thread_rolled_back`,
  `thread_goal_updated`, `thread_settings_applied` (the serde names
  `task_started`/`task_complete`, with aliases `turn_started`/`turn_complete`,
  are in `protocol.rs` `EventMsg`).
- **Paginated only:** every `item_completed` event, carrying a `TurnItem`.
- **Legacy only:** `user_message`, `agent_message`, `agent_reasoning`,
  `agent_reasoning_raw_content`, `patch_apply_end`, `context_compacted`,
  `mcp_tool_call_end`, `web_search_end`, `image_generation_end`,
  `entered_review_mode`, `exited_review_mode`, and non-final
  `sub_agent_activity`. Legacy files also keep a few `item_completed` events
  (function-call output, plan, sleep, completed subagent activity).
- **Never persisted:** errors, warnings, approval requests
  (`exec_approval_request`, `apply_patch_approval_request`,
  `request_permissions`, `request_user_input`), streaming deltas,
  `exec_command_begin/end`, `turn_diff`, hook start/end, MCP startup. A
  pending approval is therefore never in the log; it has to come from the
  hooks or the pane, as with Claude.

The TUI has asked for paginated history for every non-ephemeral thread since
0.147 ("Paginate TUI transcript history (#36950)", 2026-08-04;
`thread_start_params_from_config`, `tui/src/app_server_session.rs` line 2066:
`history_mode: (!config.ephemeral).then_some(ThreadHistoryMode::Paginated)`),
and the app server honours it when a state database exists
(`supports_paginated_history_lists`, `thread-store/src/local/mod.rs` line 714).
A subagent inherits its parent's mode (`core/src/agent/control/spawn.rs` line
~731). So on 0.160 a pane's file is paginated; any file from before 0.147, or
one written without the SQLite state, is legacy. Codex's own summary reader
handles both (`rollout/src/list.rs` line 1228: "Legacy rollouts persist
UserMessage while paginated rollouts persist ItemCompleted(UserMessage)").

### 3.4 `item_completed` and its items

```json
{"type":"item_completed","thread_id":"…","turn_id":"…","item":{"type":"AgentMessage",…},"started_at_ms":…,"completed_at_ms":…}
```

(`ItemCompletedEvent`, `protocol.rs` line 1947.) The item's `type` is the
Rust variant name, unrenamed (`TurnItem`, `protocol/src/items.rs` line 46,
`#[serde(tag = "type")]`). The ones claude-mux needs, with their fields from
`items.rs`:

| `item.type` | Fields | Note |
|---|---|---|
| `UserMessage` | `id`, `content: [{type:"text", text, text_elements}, {type:"local_image", path}, …]` | what the person typed. The `response_item` user messages also include AGENTS.md text and `<environment_context>`; use this item instead |
| `AgentMessage` | `id`, `content: [{type:"Text", text}]`, `phase` (`"commentary"` or `"final_answer"`, may be absent) | |
| `Reasoning` | `id`, `summary_text: [string]`, `raw_content: [string]` | summaries only; the full reasoning is encrypted in the `response_item` |
| `CommandExecution` | `id` (the call id), `command: [argv]`, `cwd` (a **`file://` URI**), `parsed_cmd`, `source` (`agent`, `user_shell`, …), `status` (`completed`/`failed`/`declined`), `aggregated_output`, `exit_code`, `duration` (`{secs, nanos}`); in 0.160 also `stdout`, `stderr`, `formatted_output` | `PathUri` serialises as a URI (`utils/path-uri/src/lib.rs` line 689). On `main` (0.162+) `stdout`/`stderr`/`formatted_output` are gone and `aggregated_output` is cut to 64 KiB with a marker (`main:codex-rs/rollout/src/policy.rs`, `PERSISTED_COMMAND_OUTPUT_MAX_BYTES`) |
| `FileChange` | `id`, `changes: {<abs path>: {type:"add",content} \| {type:"delete",content} \| {type:"update",unified_diff,move_path}}`, `status`, `stdout`, `stderr` | §4 |
| `McpToolCall` | `id`, `server`, `tool`, `arguments`, `status`, `result`, `error`, `duration` (camelCase fields) | results capped at 64 KiB on `main` |
| `DynamicToolCall`, `WebSearch`, `ImageView`, `ImageGeneration`, `Plan`, `HookPrompt`, `EnteredReviewMode`/`ExitedReviewMode`, `Extension` | | render as generic tool rows |
| `CollabAgentToolCall` | `id`, `tool` (`spawn_agent`, `send_input`, `wait`, `close_agent`, `resume_agent`, …), `status`, `sender_thread_id`, `receiver_thread_ids`, `receiver_agents: [{thread_id, agent_nickname, agent_role}]`, `prompt`, `model`, `reasoning_effort`, `agents_states` | §7 |
| `SubAgentActivity` | `id`, `kind` (`started`/`interacted`/`interrupted`/`completed`), `agent_thread_id`, `agent_path` | multi-agent v2 |
| `ContextCompaction` | `id` | §3.6 |

The `item_completed` for an item has the matching `response_item` beside it
(the raw `function_call` with its JSON-string `arguments` and `call_id`, then
`function_call_output`). For a transcript, read the items; read the raw
records only for what the items lack. The shell tool is `exec_command` by
default (unified exec is stable and on, `features/src/lib.rs`), but tool names
depend on the model's configuration, which is another reason to read
`CommandExecution` rather than tool names.

### 3.5 Turns, interruptions and errors

- A turn opens with `task_started {turn_id, started_at (unix s), model_context_window, collaboration_mode_kind}`
  and closes with `task_complete {turn_id, last_agent_message, error?, started_at, completed_at, duration_ms, time_to_first_token_ms}`
  or `turn_aborted {turn_id, reason, …}` where `reason` is `interrupted`
  (Escape), `replaced`, `review_ended` or `budget_limited`
  (`protocol.rs` lines 2153–2197, 4257–4285).
- A failed turn carries `error: {message, codex_error_info}` on its
  `task_complete` (`ErrorEvent`, `protocol.rs` line 2075). Standalone `error`
  and `warning` events are not persisted (§3.3).
- `thread_rolled_back {num_turns}` records an undo of the last turns.

`turn_aborted` with `interrupted` is the log's equivalent of Claude's
"[Request interrupted by user]" line, which `interruptNote()` in
`src/transcript/parser.ts` reads.

### 3.6 Compaction

A compaction writes a `compacted` line (`message`: the summary text;
`replacement_history`: the retained items, which can be large) followed by a
fresh `turn_context`, and in paginated files an `item_completed` with a
`ContextCompaction` item (`core/src/session/mod.rs` lines ~4150–4200;
`history/src/lib.rs` `CompactedItem`). This maps onto the parser's `compact`
entry, with `message` as the summary. Whether it was manual (`/compact`) or
automatic is not on the line; Codex's `PreCompact`/`PostCompact` hooks say
(`compaction_trigger_label`, `core/src/hook_runtime.rs`).

### 3.7 Mapping onto `TranscriptEntry`

| claude-mux entry (`src/transcript/parser.ts`) | Paginated Codex | Legacy Codex |
|---|---|---|
| `user` | `item_completed` `UserMessage` | `event_msg` `user_message.message` |
| `queued` | no equivalent found in the log: Codex's own pending-input queue is a transient event (`thread_queue_changed`) and lives in `queue_1.sqlite` | same |
| `interrupt` | `turn_aborted` with `reason: "interrupted"` | same |
| `compact` | `compacted` (+ `ContextCompaction`) | `compacted` (+ `context_compacted`) |
| `text` | `AgentMessage` | `agent_message.message` |
| `thinking` | `Reasoning.summary_text` | `agent_reasoning.text` |
| `tool` | `CommandExecution`, `McpToolCall`, `DynamicToolCall`, `WebSearch`, … (result inside the item) | `response_item` `function_call` + `function_call_output`, paired by `call_id` |
| `tool.patch` | `FileChange.changes` | `patch_apply_end.changes` |
| `ask` | **unverified**: `request_user_input` is not persisted; whether an answered question leaves a durable item was not traced | |
| `peer` | `inter_agent_communication` lines (multi-agent v2) | |

Unlike Claude Code, Codex does not split one assistant response into several
lines that must be folded by message id: each item arrives once, complete.

## 4. File edits for the Changes pane

Edits are made with the `apply_patch` tool (Codex's own `*** Begin Patch`
format, sent as a `custom_tool_call` whose `input` is the patch). When the
patch has been applied, `emit_patch_end()` completes a `FileChange` item
(`core/src/tools/events.rs` lines 622–640) built by
`convert_apply_patch_to_protocol()` (`core/src/apply_patch.rs` lines 64–89):

- keys are absolute paths (the action's paths are joined to the effective cwd,
  `apply-patch/src/invocation.rs`);
- `update.unified_diff` is `similar`'s unified diff with context radius 1 and
  no file headers: `@@ -1 +1 @@\n-old\n+new\n`
  (`unified_diff_from_chunks_with_context_and_mode`,
  `apply-patch/src/file_update.rs` line 308; tests in `file_update_tests.rs`);
- `add.content` is the whole new file; `delete.content` is the old file;
- `move_path` is set for a rename;
- `status` is `completed`, `failed` or `declined`. A declined or failed patch
  still completes an item, so filter on `completed`.

So `src/transcript/changes.ts` can count additions and deletions from the
diff's `+`/`-` lines, and an `add` as all lines added, exactly as it does for
a Claude `Write` with `type: "create"`. Edits made through the shell (`sed
-i`, a script) are not in any item, the same blind spot as Claude's Bash; the
git source covers them. Grouping by turn uses `item_completed.turn_id`.

## 5. Past sessions

### 5.1 The state database (cheapest)

`~/.codex/state_5.sqlite`, table `threads`, columns as created by
`state/migrations/0001_threads.sql` through `0058` and confirmed on omarchy:
`id`, `rollout_path`, `created_at(_ms)`, `updated_at(_ms)`, `recency_at(_ms)`,
`source`, `thread_source`, `model_provider`, `model`, `reasoning_effort`,
`cwd`, `title`, `name`, `first_user_message`, `preview`, `tokens_used`,
`has_user_event`, `archived`, `archived_at`, `git_sha`, `git_branch`,
`git_origin_url`, `cli_version`, `agent_nickname`, `agent_role`,
`agent_path`, `history_mode`, `originator`, `is_pinned`, project and section
columns. `thread_spawn_edges(parent_thread_id, child_thread_id, status)` links
subagents to parents (`0021_thread_spawn_edges.sql`).

One read-only query gives the whole list. Caveats:

- The database is WAL-mode SQLite written by a running Codex, so open it
  read-only and expect `-wal`/`-shm` files beside it.
- Migrations rename it (`state_5` today; `STATE_DB_FILENAME`,
  `state/src/sqlite.rs`). A reader should look for the highest
  `state_*.sqlite` and fall back to files.
- Rows are reconciled from rollouts; whether every column is current at every
  moment of a live session was not traced (**unverified**). For live sessions
  claude-mux reads the rollout anyway.

### 5.2 The files (Codex's own fallback)

`read_head_summary()` (`rollout/src/list.rs` lines 1133–1256) reads the first
10 lines, and up to 200 more until it has seen a user message, taking cwd,
git, source, CLI version and creation time from `session_meta` and the first
prompt from the first `UserMessage` (either dialect). A cheap reader for
claude-mux, like `readPastSession()` in `src/transcript/past-sessions.ts`:

- **head**: line 1 (`session_meta`) is large because of `base_instructions`;
  the 64 KiB `END_BYTES` window may not reach the first prompt, which follows
  several kilobytes of injected AGENTS.md and environment text. Read lines
  until the first `UserMessage`/`user_message` instead of a fixed byte count.
- **tail**: the last line's `timestamp` is the last activity; the latest
  `turn_context` gives the current cwd and model.
- **leave out** files whose `source` is not interactive (`exec`, `mcp`,
  subagents), the analogue of skipping Claude's `-p`/SDK transcripts. A
  subagent's rollout sits in the same date folders as root threads, so this
  filter is required, not optional.

### 5.3 Titles

A name set with `/rename`, or generated by the TUI after the first prompt (a
side request to `gpt-5.6-luna`, max 36 characters,
`tui/src/app/thread_title.rs`; it never overwrites a name the person gave), is
saved with `thread/name/set`, which appends to `session_index.jsonl` in both
dialects and updates `threads.name` (`thread-store/src/local/update_thread_metadata.rs`
lines ~150–230). Read `session_index.jsonl` from the end; the last entry per
id wins. Without a name, `first_user_message` (or `preview`) stands in, as
the first prompt does for Claude.

### 5.4 Resume

- `codex resume <SESSION_ID>`: "Session id (UUID) or session name. UUIDs take
  precedence if it parses." `--last` picks the most recent in the current
  directory, `--all` drops the cwd filter (`ResumeCommand`, `cli/src/main.rs`
  line 350; CLI reference: "Continue a previous interactive session by ID or
  resume the most recent chat"). It does not take a file path, unlike
  claude-mux's `claude --resume <transcript>`.
- If the current directory differs from the session's latest cwd, the TUI asks
  which to use (`resolve_cwd_for_resume_or_fork`, `tui/src/session_resume.rs`;
  `tui/src/cwd_prompt.rs`). Starting the tmux session in the recorded cwd
  avoids the prompt; so does `[tui] resume_cwd = "session"` (passable as
  `-c tui.resume_cwd=session`; `ResumeCwdMode`, `config/src/types.rs` lines
  96 and 931).
- A thread already written by a live process cannot get a second writer:
  `WriterLockCoordinator::acquire` fails with "thread … already has an active
  writer" (`rollout/src/writer_lock.rs`). claude-mux's `planResume()` should
  still answer with the live pane first, as it does for Claude. Testing
  whether the lock is held (`/proc/locks`, or a non-blocking `flock` that is
  released at once) is a liveness probe that needs no hook (**unverified
  live**).
- `codex fork <id>` copies a thread into a new one; `codex delete` removes the
  transcript (CLI reference).
- No retention cleanup of rollouts, like Claude Code's 30-day deletion, was
  found: `rollout/src/maintenance.rs` only coordinates compression and
  migration, and deletion goes through `codex delete` / `thread/delete`
  (`thread-store/src/local/delete_thread.rs`). **Unverified** beyond that
  reading.

## 6. Token usage and model

- **`token_usage_record`** (since 0.153, "Persist response token usage in
  rollout history (#41912)"): `{thread_id, turn_id, session_id, root_turn_id,
  response_id, usage, turn_token_usage, thread_token_usage}`, one per model
  response that reported usage (`TokenUsageRecord`, `protocol.rs` line 2264;
  written by `record_observed_response_completed`,
  `core/src/session/mod.rs` lines 4769–4800). `usage` is that response alone;
  the other two are running totals. Sum `usage`, keyed by `response_id`
  against repeats, which plays the role of the `message.id:requestId` key in
  `src/usage/transcripts.ts`.
- **`token_count`** events (all versions): `{info: {total_token_usage,
  last_token_usage, model_context_window}, rate_limits}` (`TokenCountEvent`,
  `TokenUsageInfo`, `protocol.rs` lines 2276–2346). For files older than 0.153
  this is the only source; sum `last_token_usage`. **Unverified:** whether a
  `token_count` can repeat the same `last_token_usage` (for example on a
  rate-limit-only refresh), which would overcount; compare
  `total_token_usage` between events to detect it.
- **`TokenUsage`** fields: `input_tokens`, `cached_input_tokens`,
  `cache_write_input_tokens`, `output_tokens`, `reasoning_output_tokens`,
  `total_tokens` (`protocol.rs` line 2241). `input_tokens` includes the cached
  part: Codex's `non_cached_input()` is `input_tokens - cached_input_tokens`
  and `blended_total()` is non-cached input plus output (`protocol.rs` lines
  2430–2437), which also shows reasoning tokens are counted inside
  `output_tokens`. Mapped to claude-mux's `TokenTotals`
  (`src/usage/pricing.ts`): `uncachedInput = input − cached`, `cacheRead =
  cached`, `cacheCreation5m = cache_write_input_tokens` (no 1h tier), `output =
  output_tokens`, `thinking = reasoning_output_tokens`.
- **Model**: from the `turn_context` line with the same `turn_id` (`model`,
  `effort`; `TurnContextItem`, `protocol.rs` line 3301). Per-response
  re-routing is reported only by the transient `model_reroute` event, so a
  rerouted response is attributed to the turn's model (**limitation**).
- **Cost**: the rollout records no dollar amount. OpenAI model rates would
  have to join claude-mux's rate table.
- **Context meter**: `last_token_usage.total_tokens` against
  `model_context_window` (Codex's own `tokens_in_context_window()` is
  `total_tokens`).
- **Plan meter**: `rate_limits` carries `primary` and `secondary` windows
  (`used_percent`, `window_minutes`, `resets_at` unix seconds), `credits`,
  `plan_type` (`RateLimitSnapshot`, `RateLimitWindow`, `protocol.rs` lines
  2349–2401). That is the Codex counterpart of the server-graded limits in
  `src/usage/quota.ts`, read straight from the log.

## 7. Subagents

Codex has them, on by default (`multi_agent`, `Stage::Stable`,
`default_enabled: true`; `multi_agent_v2` off; `features/src/lib.rs`). The
model calls `spawn_agent` (namespace `multi_agent_v1`, arguments `message`,
`agent_type`, `model`, `reasoning_effort`, `fork_context`), then `wait`
(`targets`, `timeout_ms`), `send_input`, `close_agent`, `resume_agent`
(`core/src/tools/handlers/multi_agents/*.rs`). Docs: "Use `/subagents` to
inspect and switch between agent threads while they run"; Codex "waits until
all requested results are available"
(`learn.chatgpt.com/docs/agent-configuration/subagents`).

In the logs:

- **Parent**: a `CollabAgentToolCall` item per call
  (`core/src/tools/handlers/multi_agents/spawn.rs` lines 84–195). For
  `spawn_agent` it names the child's thread id, nickname (Codex picks one,
  e.g. a scientist's name) and role, the prompt, model and effort;
  `agents_states` maps thread id to `pending_init`, `running`,
  `{"completed": "<final message>"}`, `{"errored": "…"}`, `shutdown`,
  `not_found` (`AgentStatus`, `protocol.rs` line 1823). The
  `function_call_output` of `spawn_agent` is `{"agent_id", "nickname"}`.
- **Child**: a full rollout of its own, same folder scheme, whose
  `session_meta` has `parent_thread_id`, `agent_nickname`, `agent_role`,
  `thread_source: "subagent"` and the `thread_spawn` source. Its
  `session_id` is the root's (§2.1). The state database records the edge in
  `thread_spawn_edges`.
- **Hooks**: `SubagentStart` and `SubagentStop` fire for spawned agents with
  `agent_id` (the child's thread id) and `agent_type` (its role, `default`
  when unset); `SubagentStop` carries the child's rollout as
  `agent_transcript_path` and the parent's as `transcript_path`
  (`core/src/hook_runtime.rs` lines 126–150 and 395–437). The child's own tool
  hooks arrive under the root's `session_id` with `agent_id` set. That is the
  shape claude-mux's subagent tracking already expects from Claude Code.

So claude-mux's agent window (`/session/<target>/agent/<id>`) can open the
child's rollout directly, found from the hook's `agent_transcript_path` or
from the id in the parent's `CollabAgentToolCall`.

## 9. How Codex announces its own update

- **Check**: `get_upgrade_version()` reads `~/.codex/version.json`
  (`{latest_version, last_checked_at, dismissed_version}`) and, if it is older
  than 20 hours, refreshes it in the background from
  `https://api.github.com/repos/openai/codex/releases/latest` (or the Homebrew
  cask API for a brew install). The current run uses the cached value; the
  next run shows the notice (`tui/src/updates.rs` lines 27–150,
  `tui/src/updates_cache.rs`). `check_for_update_on_startup = false` turns it
  off (`core/src/config/mod.rs` line 4073). Release builds only
  (`#![cfg(not(debug_assertions))]`).
- **Startup picker**: when an update is pending, not dismissed, and Codex
  knows how it was installed, a full-screen picker appears **before** the
  session starts (`run_update_prompt_if_needed`, `tui/src/update_prompt.rs`;
  called from `tui/src/lib.rs` line ~1174, skipped when a prompt was given on
  the command line). Its text, from the snapshot
  `tui/src/snapshots/codex_tui__update_prompt__tests__update_prompt_modal.snap`:

  ```
    Update available · 0.0.0 → 9.9.9
    Release notes: https://github.com/openai/codex/releases/latest

  › 1. Update now (runs `npm install -g @openai/codex`)
    2. Skip
    3. Skip until next version

    enter continue · esc skip
  ```

  "Update now" exits Codex and runs the command. **This screen blocks a pane
  claude-mux has just started**: claude-mux must recognise and answer it
  (Esc), or launch with `-c check_for_update_on_startup=false` and offer the
  update itself.
- **In-session card**: at session start the transcript gets a bordered card
  (`UpdateAvailableHistoryCell`, `tui/src/history_cell/notices.rs`;
  inserted by `tui/src/app/startup.rs` line ~1052):

  ```
  ✨ Update available! 0.160.0 -> 0.163.0
  Run npm install -g @openai/codex to update.

  See full release notes:
  https://github.com/openai/codex/releases/latest
  ```

  When the install method is unknown the second line is "See
  https://github.com/openai/codex for installation options."
- **Commands** (`UpdateAction::command_args`, `tui/src/update_action.rs`):
  `npm install -g @openai/codex`, `bun install -g @openai/codex`,
  `pnpm add -g @openai/codex`, `vp install -g @openai/codex`,
  `brew upgrade --cask codex`, the standalone installer
  `sh -c "curl -fsSL https://chatgpt.com/codex/install.sh | CODEX_NON_INTERACTIVE=1 sh"`,
  and `codex app-server daemon update` for the daemon. **`codex update`**
  runs whichever applies ("Check for and apply a Codex CLI update when the
  installed release supports self-update", CLI reference;
  `run_update_command`, `cli/src/main.rs` line 856).
- For claude-mux the cheapest signal is machine-wide, not per pane:
  `version.json`'s `latest_version` against `codex --version`. The pane text
  above is the fallback. On omarchy Codex is installed through mise
  (`~/.local/share/mise/installs/codex/latest/bin/codex`), an install method
  Codex does not recognise, so it would print the "See …installation options"
  line and `codex update` would refuse. (Read from
  `install-context/src/lib.rs`: only the `CODEX_MANAGED_BY_NPM`/`_BUN`/`_PNPM`/`_VITE_PLUS`
  variables, a release under `~/.codex/packages/standalone/releases/`, or a
  Homebrew path on macOS give a method; anything else is `Other`, which
  `UpdateAction::from_install_context` maps to no action. Not run.)
